4. Subscription Setup -> Check Setup Order Status

## Autopay Standard Checkout (v2) Collection

Collection: PhonePe Standard Checkout Autopay v2. Uses the `/checkout/v2/...` and `/payments/v2/refund` base paths (distinct from the eMandate collection's `/subscriptions/v2/...`). Only credentials (client_id, client_version, client_secret) and tsp_env need to be set; all order/subscription/refund IDs are auto-generated by scripts on each run, and the access token is fetched automatically.

Run order:

1. Authorization -> Get Access Token
2. Subscription Setup -> Setup Subscription (generates merchant_order_id, merchant_subscription_id, subscription_expire_at; used for both API and SDK integration)
3. Subscription Setup -> Check Subscription Order Status
4. Subscription Setup -> Check Subscription Status
5. Redemption Flow -> Notify Redemption (generates redeem_merchant_order_id)
6. Redemption Flow -> Execute Redemption (only when autoDebit is false)
7. Redemption Flow -> Redemption Order Status
8. Other APIs -> Cancel Subscription (returns 204 No Content)
9. Refund -> Initiate Refund (generates merchant_refund_id)
10. Refund -> Check Refund Status

Key setup variables: `setup_amount`, `max_amount`, `frequency` (DAILY/WEEKLY/MONTHLY/... /ON_DEMAND), `auth_workflow_type` (TRANSACTION or PENNY_DROP), `redirect_url`, `redeem_amount`, `refund_amount`.

Subscription Pause/Unpause and Revoke are user-initiated from the PSP app and are not merchant-callable APIs — they arrive only as webhook callbacks. See the Webhooks (Mock Server) folder for `subscription.paused`, `subscription.unpaused`, and `subscription.revoked` examples.

Webhooks via mock server: right-click the Webhooks (Mock Server) folder -> Mock Collection, then set mock_base_url to the generated mock URL. Set webhook_auth_sha256 to SHA256(username:password) to mirror the PhonePe callback Authorization header.

## One Time Mandate (OTM) Collection

Collection: PhonePe One Time Mandate (OTM) v2. OTM is a "hold now, charge later" flow for UPI: the Pay call authorizes (holds) funds with `paymentFlow.delayedCapture=true`, and you later Capture (full or partial) or Cancel to release the hold. Uses the `/payments/v2/...` base path. Only credentials (client_id, client_version, client_secret) and tsp_env need to be set; merchantOrderId is auto-generated on each Pay run, orderId/transactionId are captured from responses, and the access token is fetched automatically.

Run order:

1. Authorization -> Get Access Token
2. OTM Payment -> Initiate OTM Authorization (Pay) (generates merchant_order_id; captures order_id, transaction_id, otm_intent_url)
3. Status -> Check Order Status (poll until transaction state is AUTHORIZED)
4. OTM Payment -> Capture Authorized Payment (only when state is AUTHORIZED; partial capture allowed) OR OTM Payment -> Cancel Authorized Payment (returns 202 Accepted, releases the hold)
5. Status -> Check Order Status / Check Transaction Status (verify COMPLETED or FAILED)

Key variables: `otm_amount` (authorization amount, min 100 paise), `otm_capture_amount` (capture amount, <= authorized), `otm_expire_after` (300-5184000 seconds), `merchant_user_id`, `device_os`, `redirect_url`, `cancel_redirect_url`. Pay `paymentMode.type` supports UPI_INTENT (returns intentUrl) or UPI_QR (returns qrData).

Order/transaction states: AUTHORIZATION_IN_PROGRESS -> AUTHORIZED -> CAPTURE_IN_PROGRESS -> COMPLETED, or CANCEL_IN_PROGRESS -> FAILED (PAYMENT_CANCELLED). Capture only works from AUTHORIZED; other states return INVALID_TRANSACTION_STATE. Wait for the authorization webhook before capturing.

Webhooks via mock server: right-click the Webhooks (Mock Server) folder -> Mock Collection, then set mock_base_url to the generated mock URL. Set webhook_auth_sha256 to SHA256(username:password) to mirror the PhonePe callback Authorization header. Supported events: pg.order.completed, pg.order.failed, pg.transaction.failed (plus pg.transaction.authorized for the authorization notification).

UAT Sandbox templates (Flow: Custom & Standard Checkout V2, search "One Time Mandate"): Capture -> "OTM UPI Intent Capture Success" / "OTM QR Intent Capture Success" (and matching Failure); Cancel -> "OTM UPI Intent Cancel Success" / "OTM QR Intent Cancel Success" (and matching Failure).

## PG V2 Payment Links Collection

Collection: PhonePe PG V2 Payment Links. A Payment Link is a shareable, PhonePe-hosted checkout URL you generate via API and send to a customer (SMS/email/WhatsApp); they pay with UPI, Cards, or NetBanking with no site/app integration on your side. Uses the `/paylinks/v1/...` base path (plus `/payments/v2/refund` for refunds). Only credentials (client_id, client_version, client_secret) and tsp_env need to be set; merchantOrderId is auto-generated on each Create run, orderId/paylinkUrl are captured from responses, and the access token is fetched automatically.

Run order:

1. Authorization -> Get Access Token
2. Payment Links -> Create Payment Link (generates merchant_order_id and paylink_expire_at; captures order_id, paylink_url)
3. Share paylink_url with the customer (or Payment Links -> Notify Customer to re-send over SMS/email)
4. Payment Links -> Check Payment Link Status (poll until state is COMPLETED/FAILED/EXPIRED; details=true returns every attempt)
5. Payment Links -> Cancel Payment Link (deactivate an ACTIVE link) OR Refund -> Initiate Refund / Check Refund Status (for a COMPLETED payment)

Key variables: `paylink_amount` (paisa, min 1), `paylink_expire_at` (epoch ms; auto-defaulted to 7 days, max 45 days from now), `customer_name`, `customer_phone` (formats `+9197xxxxxx89` or `97xxxxxx89`, no spaces/hyphens), `customer_email`, `refund_amount` (paisa, min 100, <= captured), `merchant_refund_id` (auto-generated). Set `notificationChannels.SMS`/`EMAIL` to true in the Create body to have PhonePe deliver the link.

Link states: ACTIVE -> COMPLETED, or ACTIVE -> FAILED / EXPIRED / CANCELLED. Always rely on the top-level `state` to confirm the outcome. Refund states: PENDING -> COMPLETED / FAILED.

Partner integrations: add an `X-MERCHANT-ID` header (end merchant's MerchantID) on every call.

Webhooks via mock server: right-click the Webhooks (Mock Server) folder -> Mock Collection, then set mock_base_url to the generated mock URL. Set webhook_auth_sha256 to SHA256(username:password) to mirror the PhonePe callback Authorization header. Supported events: paylink.order.completed, paylink.order.failed.

UAT Sandbox (PhonePe Test app, Flow: B2B PG Payment Links; templates start with keyword "Paylink"): default success is "Default Paylink Success". Test amount limits Rs.1-Rs.1000; card OTP 123456; NetBanking bankId SBIN, username/password test/test.

## PG V2 Standard Checkout Collection

Collection: PhonePe PG V2 Standard Checkout. The fastest way to accept a one-time payment: you create an order and PhonePe returns a hosted PayPage `redirectUrl` where the customer completes payment (UPI/Cards/NetBanking) - PhonePe renders the whole checkout UI. Uses the `/checkout/v2/...` base path for pay and order status (plus `/payments/v2/refund` for refunds). Only credentials (client_id, client_version, client_secret) and tsp_env need to be set; merchantOrderId is auto-generated on each Create run, orderId/redirectUrl are captured from responses, and the access token is fetched automatically.

Run order:

1. Authorization -> Get Access Token
2. Payment -> Create Payment (paymentFlow.type PG_CHECKOUT; generates merchant_order_id; captures order_id, checkout_redirect_url)
3. Redirect the customer to checkout_redirect_url (the hosted PayPage) to complete payment
4. Status -> Check Order Status (poll until state is COMPLETED/FAILED; details=true returns every attempt)
5. Status -> Check Order Status with Settlement (adds settlementDetails=true to also return the settlement state / breakup once the payment is settled)
6. Refund -> Initiate Refund / Check Refund Status (for a COMPLETED payment)

Key variables: `checkout_amount` (paisa, min 100), `expire_after` (seconds, 300-3600), `redirect_url` (post-payment return URL), `refund_amount` (paisa, min 100, <= captured), `merchant_refund_id` (auto-generated). `settlement_state` is captured from the settlement status response.

Order states: PENDING -> COMPLETED or FAILED. Refund states: PENDING -> COMPLETED / FAILED. Always rely on the top-level `state`.

Partner integrations: add an `X-MERCHANT-ID` header (end merchant's MerchantID) on every call.

Webhooks via mock server: right-click the Webhooks (Mock Server) folder -> Mock Collection, then set mock_base_url to the generated mock URL. Set webhook_auth_sha256 to SHA256(username:password) to mirror the PhonePe callback Authorization header. Supported events: checkout.order.completed, checkout.order.failed, pg.refund.completed, pg.refund.failed.

## PG V2 Custom Checkout Collection

Collection: PhonePe PG V2 Custom Checkout. API-only integration where you build your own payment UI and drive each instrument directly: create an order with a chosen paymentMode (UPI Intent, UPI Collect, UPI QR, Card, or NetBanking) and PhonePe returns the artifact for that mode (intentUrl, qrData, or a redirectUrl). Uses the `/payments/v2/...` base path for pay, order status and refunds. Only credentials (client_id, client_version, client_secret) and tsp_env need to be set; merchantOrderId is auto-generated on each pay run, orderId is captured from responses, and the access token is fetched automatically.

Key differences from Standard Checkout: `paymentFlow.type` is `PG` (not `PG_CHECKOUT`) and the base path is `/payments/v2` (not `/checkout/v2`). `merchantUrls.redirectUrl` is mandatory only for Card and NetBanking. Card payments are PCI-DSS scoped - card number/CVV must be RSA-4096 encrypted, and in PRODUCTION the Card pay endpoint host is `https://cards.phonepe.com/apis/pg/payments/v2/pay` (override api_base_url for that call).

Run order:

1. Authorization -> Get Access Token
2. Payment -> pick one: Pay - UPI Intent (opens intentUrl), Pay - UPI Collect (pushes to customer_vpa), Pay - UPI QR (renders qrData), Pay - Card (RSA-encrypted card + 3DS redirect), or Pay - NetBanking (bank_id + redirect). Each generates merchant_order_id and captures order_id.
3. Status -> Check Order Status (poll until state is COMPLETED/FAILED; details=true returns every attempt)
4. Status -> Check Order Status with Settlement (adds settlementDetails=true to also return the settlement state / breakup once the payment is settled)
5. Refund -> Initiate Refund / Check Refund Status (for a COMPLETED payment)

Key variables: `checkout_amount` (paisa, min 100), `expire_after` (seconds), `device_os` (ANDROID/IOS), `target_app` (UPI app for Intent), `customer_vpa` (for UPI Collect), `bank_id` (for NetBanking, e.g. HDFC), `redirect_url` (Card/NetBanking return URL), `merchant_user_id`, `refund_amount`, `merchant_refund_id` (auto-generated). Card requests contain RSA-encryption placeholders that must be replaced with real encrypted values.

Order states: CREATED -> PENDING -> COMPLETED or FAILED. Refund states: PENDING -> COMPLETED / FAILED. Always rely on the top-level `state`.

Partner integrations: add an `X-MERCHANT-ID` header (end merchant's MerchantID) on every call.

Webhooks via mock server: right-click the Webhooks (Mock Server) folder -> Mock Collection, then set mock_base_url to the generated mock URL. Set webhook_auth_sha256 to SHA256(username:password) to mirror the PhonePe callback Authorization header. Supported events: pg.order.completed, pg.order.failed, pg.refund.completed, pg.refund.failed.

## PG V2 Settlement Collection

Collection: PhonePe PG V2 Settlement. Reconcile the money PhonePe pays out to your bank account and (optionally) split a single payment across multiple linked accounts. Uses the `/settlements/v1/...` base path (plus `/checkout/v2/...` for split-settlement payments). Only credentials and tsp_env need to be set; the access token is fetched automatically.

Run order (Settlement):

1. Authorization -> Get Access Token
2. Settlement -> Date Range Settlement IDs (from/to auto-default to the last 30 days; captures the first `settlement_id`)
3. Settlement -> Settlement Status (status of that settlement_id)
4. Settlement -> Settlement Transactions (line items that make up the settlement)

Run order (Split Settlement):

1. Split Settlement -> Get Split Account Info (fetch linked accountIds; copy into split_account_id_1/2)
2. Split Settlement -> Split Validation (validate the split before paying)
3. Split Settlement -> Initiate Payment with SplitInfo (Standard Checkout order carrying splitSettlementInfo)
4. Split Settlement -> Order Status with SplitInfo (returns the split breakup)

Key variables: `settlement_from` / `settlement_to` (epoch ms, auto-defaulted), `settlement_id`, `split_type` (ABSOLUTE = paisa, PERCENT = percentages), `split_account_id_1` / `split_account_id_2`, `split_value_1` / `split_value_2`, plus the checkout variables (`checkout_amount`, `expire_after`, `redirect_url`). Limits: date-range `limit` max 40 and window not older than 6 months; transactions `limit` max 50 with strictly sequential offsets.

Split body values use inline `//` comments as an editing guide - remove the comments (or use the request description) before firing real requests, since PhonePe expects strict JSON.

## PG V2 Chargeback (Disputes) Collection

Collection: PhonePe PG Chargeback (Disputes). Track and respond to customer chargebacks. Uses the `/v1/disputes/...` base path. Only credentials and tsp_env need to be set; the access token is fetched automatically.

Run order:

1. Authorization -> Get Access Token
2. Disputes -> Fetch List of Disputes (from/to auto-default to the last 30 days; filter by dispute_status)
3. Disputes -> Fetch Dispute (single dispute by dispute_id)
4. Disputes -> Accept Dispute OR Contest Dispute
5. Evidence -> Upload Evidence (multipart file; captures evidence_id) / Delete Evidence

Key variables: `dispute_id`, `evidence_id`, `dispute_status` (ACTION_REQUIRED / UNDER_REVIEW / WON / LOST), `contest_type` (FULL_CONTEST / PARTIAL_CONTEST), `contest_amount` (paise), `evidence_type`, `evidence_label`, `settlement_from` / `settlement_to` (list window). Request bodies now match the PhonePe chargeback docs: Accept has no body (only allowed in ACTION_REQUIRED state), Contest sends `type` + `contestAmount` (paise; ignored for FULL_CONTEST), and Upload Evidence is `multipart/form-data` with `file` (max 2MB) + `type` + `label`.

Webhooks via mock server: same setup as the other collections (Mock Collection -> mock_base_url -> webhook_auth_sha256). Events: `payment.dispute.created` / `action_required` / `under_review` / `won` / `lost`.

## PG Health Check Collection

Collection: PhonePe PG Health Check. Poll the real-time status (UP / DOWN) of payment flows and instruments so you can hide impacted payment methods and improve conversion. Only credentials and tsp_env need to be set; the access token is fetched automatically.

Run order:

1. Authorization -> Get Access Token
2. Health -> Health Check (GET /v3/health)

Important host difference: the Health Check API uses a dedicated host on production - `https://api.phonepe.com/apis/pg-health/v3/health` (sandbox stays on `https://api-preprod.phonepe.com/apis/pg-sandbox/v3/health`). The collection pre-request script sets `health_base_url` accordingly, so the standard `api_base_url` is not used for this call. The response returns `paymentFlows[]` (PAYMENT / SUBSCRIPTION_SETUP) and `instruments[]` (UPI / NETBANKING / cards) with UP/DOWN status and bank-level downtime.

## Native OTP Collection

Collection: PhonePe PG Native OTP. Keeps the customer on your page during card authentication - you collect the OTP and submit it via API instead of redirecting to the bank 3DS page. The card payment itself is created through the Custom Checkout Pay API with the extra `nativeOtp` flag (see the Custom Checkout collection and https://developer.phonepe.com/native-otp/sample-payload).

Run order:

1. Authorization -> Get Access Token
2. Native OTP -> Submit OTP (POST /payments/v2/native-otp/submit), Resend OTP (POST /payments/v2/native-otp/resend)

Key variables: `merchant_order_id` (the in-progress card payment), `otp` (sandbox test OTP: 123456). Resend allows up to 3 attempts.

## Payment Links Via Autopay Collection

Collection: PhonePe PG Payment Links Via Autopay. Sets up a UPI Autopay mandate through a shareable payment link (SMS / Email); you later notify and execute recurring redemptions.

Run order:

1. Authorization -> Get Access Token
2. Subscription Setup -> Setup Subscription (Paylink) (POST /paylinks/v1/pay)
3. Redemption -> Notify Redemption (POST /checkout/v2/subscriptions/notify), then after the mandatory 24h gap Execute Redemption (POST /checkout/v2/subscriptions/redeem)
4. Status -> Order Status (GET /checkout/v2/order/{merchantOrderId}/status)

Key variables: `paylink_amount`, `customer_name` / `customer_phone` / `customer_email`, `merchant_subscription_id`, `auth_workflow_type`, `frequency`, `max_amount` (max 1500000 paise), `redemption_amount`. `merchant_order_id`, `merchant_subscription_id` and `redemption_order_id` are auto-generated per run.

## API for Aggregators Collection

Collection: PhonePe API for Aggregators. Onboards and reads sub-merchants under an aggregator. Unlike the PG V2 APIs, these legacy endpoints authenticate with the `X-VERIFY` checksum header and a Base64-encoded request payload - NOT the O-Bearer token.

Authentication (X-VERIFY): `SHA256(base64Payload + endpointPath + saltKey) + "###" + saltIndex`. The pre-request scripts build the Base64 payload and X-VERIFY for you using Postman's built-in CryptoJS.

Run order:

1. Sub-merchant -> Create Sub-merchant (POST /v1/submerchant)
2. Sub-merchant -> Read Sub-merchant (GET /v1/submerchant/{merchantId}/{subMerchantId})

Key variables: `aggregator_base_url` (CONFIRM the exact aggregator host with your PhonePe POC), `aggregator_salt_key`, `aggregator_salt_index`, `merchant_id`, `aggregator_sub_merchant_id`, `submerchant_full_name`, `submerchant_display_name`, `submerchant_mcc`. `sub_merchant_id` is captured from the Create response for use in Read.

## A note on inline comments in request bodies

Several collections keep helpful `//` comments inside the raw JSON request bodies (e.g. `"amount": 10000, // enter your amount here`). Postman strips these `//` comments before sending, so the request still goes through and returns 200 OK - the "Fix request body JSON" hint in the editor is only a linter suggestion and can be ignored. The comments document what each field expects.
